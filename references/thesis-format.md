# 论文写作格式规范

在起草、修改、润色、审查或转换软件工程/专业硕士中文学位论文内容时加载本文件。引用格式另见 `citation-style.md`。

## 总表述标准

- 先定义边界，再写结论。涉及系统能力、性能、安全性、可用性和创新点时，必须说明适用范围，例如“原型系统”“给定实验环境”“实验室测试链”或具体支持的协议/资源类型。
- 先写本文工作，再写已有能力。使用成熟协议、框架、数据库、中间件、安全机制、分布式账本或第三方工具时，不得把已有技术能力写成本人创新。
- 先写可验证事实，再写价值判断。不能用没有实验、文献或设计支撑的形容词替代论证。
- 正式成果只呈现研究对象、研究现状、方案设计、实现验证和结论，不写项目迭代过程、方向调整过程、内部约束说明或写作自我辩护。
- 控制面和数据面边界要明确。配置中心、数据库、中间件、网关、审计组件和外部服务各自的授权边界必须与架构一致。
- 避免绝对化承诺。优先使用“缓解”“降低”“提供核验线索”“在约束条件下保证”，不要写“彻底解决”“完全消除”“绝对保证”。

## 学位论文结构

软件工程或专业硕士论文推荐结构如下，可按学校模板微调标题。

```text
第 1 章 绪论
  1.1 选题背景和工程应用价值
  1.2 国内外研究和有关技术现状
  1.3 本文的主要工作
  1.4 论文组织结构
第 2 章 相关技术介绍和选型分析
第 3 章 需求分析
  3.1 系统概述
  3.2 需求导出
  3.3 功能需求
  3.4 非功能需求
  3.5 小结
第 4 章 系统概要设计
  4.1 设计原则
  4.2 系统静态结构
  4.3 系统动态结构
  4.4 系统数据模型
  4.5 [其它]（如系统安全架构）
第 5 章 系统详细设计与实现
第 6 章 系统测试
第 7 章 总结与展望
参考文献
```

## 页面、标题和图表

- 以学校或学院正式模板为最高优先级；样例论文只能作为结构、表达和排版参考。
- 正文通常使用 A4 页面，中文正文宋体小四，英文 Times New Roman，小四或约 `12 pt`，首行缩进 2 个汉字。
- 章标题形如`第 3 章 需求分析`，章号与标题之间保留空格；二级标题形如`3.1 系统概述`；三级标题形如`6.1.1 测试环境`。
- 图题位于图下方，表题位于表上方；正文引用应写“如图 3-2 所示”“如表 3-1 所示”，不要写“如下图”“如下表”。
- 论文正文图表按章编号，例如`图3-2`、`表3-1`；图题、表题不得与图表分离。
- 摘要中不使用公式、图表和参考文献；中文关键词 3-5 个，关键词之间空一格。

## 章节写作要求

### 摘要与关键词

- 按问题背景、方法、系统工作、验证结果和结论的顺序压缩表达。
- 不写引用、不写项目过程、不写需要额外实验支撑的宽泛评价。
- 关键词使用稳定技术名词。

### 绪论

- 从真实应用需求和技术矛盾进入，再收束到论文研究对象。
- 区分背景意义、现有问题、研究内容和主要工作，不要过早展开模块设计或实现步骤。
- 写工程价值时，应落在论文原型和实验验证边界内；没有生产部署证据时，不写生产级或商业级承诺。
- 提到的数据、技术方案，一定要有资料来源，最好是有文献[J]或者技术标准白皮书[R]等，最次也得有[ER/OL]支撑。产品可以用官方技术文档首页。
- 尽量不要出现\supercite{3,4,5}\supercite{7,8,9,10,11}这种一个地方引用多篇文献。分到关键词上，或者每个引用一句话。

#### 选题依据和应用价值

这里给出大致的论证思路：
首先，从技术、产业、业态当前现状入手，说明技术有多么的受欢迎或者产业有多么繁荣（用数字说话，市场规模、数量等等，要有资料支撑）。然后，指出存在的一些问题，即对产业继续发展的制约因素、业务模态可以优化的地方等等，目的是为本项目做铺垫。进而，可以引入什么技术、什么设计、什么调整，对这些东西做初步简要的阐述（不用像国内外现状那么详细），例如引入区块链，解决了什么问题。最后，陈述本文提出的新idea，对本项目做的东西进行精要的概括了，并点出本项目的应用价值。

#### 国内外研究现状

- 按领域或问题拆分，再在每个方面内部保持时间顺序。
- 选取有代表性的、里程碑式的研究、标准、协议、工具和工程实践，不堆砌所有已收集资料。
- 国内和国外研究可划分成两个小点分别阐述，例如`1.2.x.1 国外研究现状`和`1.2.x.2 国内研究现状`。该划分只作为组织形式，不做高低比较。
- 每个段落可按“已有进展 -> 技术特点 -> 仍存在的问题”展开。标准、协议和工程产品说明能力边界；论文说明研究对象和贡献。
- 每个领域或方面最后小结当前研究还存在的问题和不足，但不要在这里陈述本文方案。
- 研究现状小结中不得出现“本文因此”“对本文而言”“与本研究相比”“本文吸收”“成果支撑本文”等表述。与本文工作的衔接放到主要工作或章末总述。

### 相关技术与技术选型

- 说明技术是什么、为什么相关、在论文中的使用边界是什么。
- 不把相关技术介绍写成产品宣传。
- 区分标准/协议和实现工具。标准可定义能力，工具只说明一种实现路径。
- 技术来源可以是文献调研，也可以是项目已经采用的依赖、协议、框架、数据库、中间件、部署方式或运行机制。
- 对项目已采用的关键技术，必须补充该技术及同类技术调研，说明可替代方案、选择依据和适用边界，不能只写“项目使用了该技术”。
- 写技术选型时，区分“系统使用的已有能力”和“本文完成的设计集成”。
- 技术选型应承接国内外研究现状或相关技术介绍，形成“问题/约束 -> 同类方案 -> 选型理由 -> 本文使用方式”的逻辑链路。

### 需求分析

- 需求概述可以描述系统业务。
- 从角色、资源、用例、业务流程、数据流、运行场景和约束推导功能需求。
- 需求尽量保持方案中立。除非是硬约束，不要把详细模块设计写成需求。
- 需求应可追踪到研究发现、设计目标或场景约束。
- 功能需求可使用 UML 用例图、用例描述表、业务流程图、活动图或顺序图；论文中突出核心用例，不必罗列全部后台用例。

#### 功能需求 
- 分清系统的参与者，并给出总的用例表和顶层用例图
- 划分出合理的功能域，给出该域的核心功能和核心用例（给出标准用例描述表，包括名称、描述、主执行者、优先级、前置条件、后置条件、基本事件流、异常事件流、触发条件）

#### 非功能需求

- 选择若干重点质量属性，不为完整性枚举所有可能属性。
- 每个非功能需求应说明适用场景、质量目标、设计约束和后续验证方式。
- 性能需求要写清范围和指标，例如时延、吞吐、连接建立时间、资源开销、同步频率或跨组件交互频率。
- 安全需求要写清安全目标，例如身份可信、最小授权、防重放、撤销可生效、审计可核验、隐私最小化或密钥边界。
- 可靠性需求要写清故障假设和恢复行为，例如重连、重试、缓存 TTL、降级运行、配置版本同步和审计连续性。

### 系统概要设计

- 先写设计原则和设计依据，再写模块结构；强调为什么采用该方案，而不是直接描述怎么做。
- 静态结构可包括功能视图、逻辑视图、逻辑分层架构、部署视图或组件图。
- 动态结构可包括核心交互顺序图、活动图、数据流图、状态转移或跨模块流程。
- 数据管理可包括 E-R 图、核心实体、关系模型、核心表结构、缓存状态和持久化边界。
- 其他特色视图可包括安全架构、外部系统边界、协议适配、异常处理或可扩展机制。

### 详细设计与实现

- 围绕核心子系统、核心模块和有特色的工程工作展开，不平均铺开所有代码。
- 每个子系统说明职责、输入输出、状态归属、依赖关系和故障边界。
- 实现细节应服务于设计说明，不能替代架构论证。
- 没有实现和测试支撑时，不写生产级高可用、商业级可扩展或完全安全。

### 系统测试

- 先说明测试环境、拓扑、版本、软硬件限制、负载、测量方法和评价口径，再呈现结果。
- 测试章节应体现测试分析、测试设计、测试执行、测试结果和测试结论。
- 测试用例应覆盖关键功能、关键非功能需求和主要异常路径。
- 评价语言要与证据强度一致。可写“验证给定环境下的可行性”，不要写“证明生产性能”。
- 对负面结果、局限和未测试边界要直接说明。

### 总结与展望

- 总结已完成工作、已验证内容和仍然存在的边界。
- 不引入新文献和新技术论断。
- 未来工作应自然来自局限，不用于弥补核心论文工作缺口。

## 禁用表达

| 禁用表达 | 问题 | 推荐口径 |
| --- | --- | --- |
| 生产级、高可用、商业级、完全安全 | 超出原型边界 | 原型级、实验验证、具备可扩展边界、降低风险 |
| 彻底解决、完全消除、绝对保证 | 绝对化 | 缓解、降低、提供核验线索、在约束条件下保证 |
| 当前课题经过方向调整后 | 项目过程性表述 | 直接描述当前研究对象和技术范围 |
| 本文不把某某作为创新点 | 自我辩护式表述 | 在创新点或主要工作中正面说明创新内容 |
| 对本文而言/本文因此/与本研究相比 | 研究现状小结过早代入本文 | 只总结现有研究不足；本文工作放到主要工作或总述中 |
| 国内资料少于国外/国内外成熟度比较 | 不必要比较 | 分别客观概括国内外研究内容和不足 |
| 这些成果支撑本文采用 | 研究现状过早转入本文方案 | 写成“相关研究表明……”并说明技术边界 |
| 某某硕士论文可作为国内学位论文线索 | 对文献作层级化标签 | 按作者和研究内容平等描述文献贡献 |

## 必须加限定的表达

| 表达 | 必须补充的限定 |
| --- | --- |
| 可行性 | 说明是原型系统、测试拓扑、实验环境下的可行性 |
| 安全 | 说明安全目标，如身份可信、授权最小、防重放、撤销可生效、审计可核验 |
| 可信 | 说明可信对象，例如身份、节点、资源、授权、撤销、配置或审计摘要 |
| 可审计 | 说明是明细与摘要关联核验，还是完整日志保存 |
| 可扩展 | 说明扩展点，例如资源类型、节点类型、授权动作、日志字段或协议适配 |
| 高效/低时延 | 必须给出指标、实验条件，或改写为具体机制效果 |
